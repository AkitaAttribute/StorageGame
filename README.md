# StorageGame

Minimal Godot 4.7.1 storage-facility exploration prototype, based on the SpaceMinerGame preview build architecture.

## Run locally
1. Install Godot 4.7.1, Python 3 and Node.js 22 (with npx).
2. Run `python tools/fetch_assets.py` (on Linux use python3).
3. Open project.godot in Godot, allow imports to finish, then run.

New Game creates an independent save slot; Continue resumes the most recently saved valid slot. Autosave every two seconds, on door interaction, and when the app loses focus or pauses. Player position, facing and animated door states are stored in user://saves. There is no save-slot selection UI yet.

Windows: WASD to move; E when near an interactive shutter. Android: SpaceMinerGame's fixed lower-right joystick; context button above it, landscape orientation. Move the mouse freely (no mouse button required) on Windows or swipe an unused area of the Android screen to orbit the third-person camera horizontally and vertically. Windows captures the cursor automatically when gameplay starts; Escape releases or recaptures it. Movement is relative to the camera. Camera orientation persists in each save. The camera maintains a fixed 3.0 m orbit radius, even behind walls. The default pitch puts the camera approximately 0.84 m above the 1.7 m character's head. Walking speed is 3.4 m/s and the animation playback rate follows actual movement. Small steps and stair risers up to 0.44 m are traversable using collision-checked step-up and floor snapping.

An additional original procedural roll-up unit (rollup_00) is placed in a clear ground footprint near the existing units when possible. Its roof height matches the imported unit geometry. The segmented corrugated curtain winds around a drum inside an overhead bay, with open/close persistence and a collision volume that follows the rising curtain. A descending rounded-wedge interaction gently moves the character sideways out of the doorway without cancelling closure. See scenes/rollup_unit.tscn and scripts/rollup_unit.gd. The downloaded starter facility is static; the four additional units on its west side are independently animated with wall and door collisions. Character is Sendagaya Shino, the official CC0 VRoid sample. The invisible Quaternius Universal Animation Library mannequin supplies human-proportioned walking and idle cycles; the runtime retargeter aligns the humanoid skeletons and grounds the support foot. This first iteration uses standard glTF materials, without MToon or hair spring physics; see assets/README.md.

## Automated builds and updates
Pushes to main and manual runs build Windows EXE, Android APK and both platform PCKs. The workflow is adapted from SpaceMinerGame's prototype/ship-builder-first-pass, using the official precompiled Windows template, Android cached development signing key, runtime checks and public preview release. The SpaceMiner-specific custom gamepad patch is not needed for this WASD prototype. The stable first autoload mounts the selected pack, and the patchable updater checks the preview manifest, validates download size, PCK magic and SHA-256, and atomically activates the verified pack. Selecting Download automatically downloads, verifies and installs the update without a second confirmation. After a successful install it displays success for three seconds, then automatically restarts on Windows or exits on Android (Godot's restart-on-exit API is desktop-only). Failures display an error and leave the game open, retaining the previous activation. The startup autoload only mounts the selected pack; the main scene loads a patchable updater after mounting. Legacy full APK/EXE builds are supported by a bridge that silences their original updater. Install the bridge update normally and reopen once; subsequent installs use the patched updater without requiring a new APK/EXE. Each published manifest references immutable build-specific PCK filenames. CI downloads and verifies the public packs before publishing the manifest; older packs remain available for cached manifests. The updater retries temporary HTTP failures without exiting. A newer complete executable or APK supersedes older installed packs. Use the full installer for engine or project configuration changes. The cache-based Android development signing key can be lost if GitHub evicts it; for durable signing, migrate to a backed-up key before distribution.

Facility GLBs are automatically dequantized to remove the unsupported KHR_mesh_quantization extension, preserving named animations. Asset files are fetched before import rather than committed as large binaries. Exports include the imported assets and do not need an asset download on first launch.

## Household objects
A fridge, textured office desk, textured screwdriver and boombox spawn on checked, unobstructed floor footprints near the current player and preferably in view. For older saves, untouched build-21 props are relocated once if far away, while moved items retain their locations. A temporary locator lists distances and directions for 60 seconds, including after grabs. Aim the center dot at a visible item within 2.1 m of the player's shoulder to highlight it. Press G on Windows or Grab on Android to move the item with the crosshair, then press again to drop it with gravity and recent motion velocity. The right arm aims toward the held item. Held objects remain dynamic, gravity-free rigid bodies with continuous collision detection and a strong acceleration-limited velocity controller; collisions, not direct transform changes, determine actual motion and release momentum. Item positions are saved with each game slot.

Household physics stability: all new or recovered objects spawn with collision disabled, are placed on checked floor positions, then activate as stationary collision bodies until grabbed. Released items remain dynamic. A solid slab and invisible prop-only boundary colliders contain movement; escaped or numerically unstable items are recovered to a clear nearby floor position. Old invalid positions are not written into saves. Layout version 4 repositions untouched legacy props once.

## Interactive containers
The refrigerator is now a hollow original cabinet with upper freezer and lower fridge compartments, shelves, gaskets and separate right-hinged doors. Aim at either door within reach and use E (Windows) or its context Open/Close button (Android); G/Grab still moves the entire refrigerator. Each hinge has its own ray-selectable collision shape on the parent rigid body, obstruction-checked movement and saved angle. The reusable scripts/hinged_panel.gd supports future container doors and lids (vertical hinge axis in this first version). Doors do not animate during rapid cabinet movement.

The refrigerator's two doors each have two modeled metal hinge assemblies: cabinet mounting leaves, rotating door leaves, interleaved barrel knuckles, pivot pins and fasteners. The hardware remains connected as each door rotates.

## Portable containers
The refrigerator is a typed container with independent fridge/freezer storage volumes. An item fully inside a closed compartment is secured in cabinet-local coordinates, without active collision or gravity. It follows translation and rotation of the cabinet and is released with normal physics once its own door opens wide enough. Saved games store the container ID, compartment and item-local transform. Containers have a cyan exterior edge outline rendered without depth testing; the temporary debug item locator is removed. The first implementation supports loose props in the refrigerator, not nested containers.

## Human locomotion
The original retargeted animation supplies base torso and finger motion. `natural_gait.gd` overrides legs using world-space planted feet, alternating stance/swing phases, terrain rays, fixed-length analytic two-bone IK and forward knee poles. It adds restrained pelvis motion and alternating arm swing, with the right-arm grab pose layered afterward. Movement speed is unchanged; faster movement uses a faster gait rather than exaggerating the donor walk. Research references: https://research.cs.wisc.edu/graphics/Papers/Gleicher/Mocap/cleanup.pdf ; https://doi.org/10.1002/cav.342 ; https://doi.org/10.1145/2538528.2538529 . This is an original simplified implementation, not a reproduction of the papers' full algorithms.

## Revised locomotion and cargo outlines
The previous procedural gait has been replaced by authored Quaternius walking with a longer, bounded cadence, upright torso constraints, relaxed arms with clothing clearance, and limited terrain/contact IK. Contact anchors are released on turning, liftoff, excessive reach, and crossing the character centerline. Movement speed remains unchanged. Implementation references: https://github.com/Johnz86/locomotion-godot (FootPlacementIK, gait/contact architecture), https://github.com/fl-wxiao/godot-rigkit (contact hysteresis and reach limits). The code is original, adapted to Shino's existing retargeter, rather than a wholesale import.
The cyan container wireframes are removed. Fully enclosed items, in open or closed compartments, are rendered to a separate camera layer and silhouette mask, with a screen-space outline visible through the container. The mask pass is disabled when there is no cargo.

Cargo is secured on the physics frame in which its compartment finishes closing, even if the cabinet has never moved. Capture allows small normal contact offsets at shelves/walls and does not reject distinct items merely because their bounding boxes overlap. Opening the compartment still restores physics once there is clearance.

Cargo attachment is event-driven: hinge closure signals capture enclosed items once, disable/remove their rigid bodies from the physics space, and reparent the original item scenes under the cabinet. Transform inheritance keeps cargo fixed automatically. The opening-clearance signal detaches and reactivates the original physics bodies. Stored-item outlines now track secured contents only and update membership on attachment/release signals; the render camera still follows the view. No per-frame containment or cargo transform synchronization is performed.

## Camera orbit
The camera now allows vertical orbit from -89.5 to +89.5 degrees relative to horizontal (near both poles, avoiding a singular look-at direction). Its normal radius remains 3 m. A sphere sweep and center ray against solid world geometry and props compress the orbit immediately when obstructed, then smoothly restore the radius when clear. The player capsule and invisible prop-only boundaries are excluded. The floor naturally limits camera distance rather than limiting viewing angle.

Container capture uses the actual model vertex envelope in cabinet coordinates rather than a padded collision box, and does not depend on velocity, sleeping or resting contact. Held items fully inside at closure are released from grab and attached. The refrigerator has an opaque center seam seal. Hinged doors retain their requested target when obstructed, pushing movable props using bounded collision sweeps or shifting the cabinet away from fixed obstacles; a completely trapped cabinet waits for clearance rather than clipping through solids. Door actions remain available when carrying another object.

Hinge obstruction reaction is now applied as a 3D contact-point force on the obstructing loose item or the cabinet, rather than a horizontal displacement. A slow velocity controller ramps load against friction and gravity, and the hinge waits for physical clearance before rotating further. A face-down fridge can lift and tilt through contact torque. There is a high finite numerical load guard for fully trapped configurations; this is a compound-body contact actuator, not a separate physical hinge joint.

The loaded hinge now advances at the same 120 degrees/second as an unobstructed hinge. Predictive contacts use the actual angular surface velocity and effective contact mass to apply immediate 3D impulses (including gravity compensation) instead of a slow force ramp followed by clearance waits. Only substantial existing penetration pauses the motor. The face-down regression now measures completion time and stalled ticks, not merely whether the cabinet eventually lifts.

## Directional walking and secondary rig clearance
The character faces the view while moving, or the held object while grabbing; idle camera orbit remains free. The old forward walk is retained, and backward, lateral and diagonal movement uses authored eight-direction UAL2 clips with phase-preserving target-pose crossfades. Forward speed stays 3.4 m/s; pure lateral movement uses 68% and pure reverse 58%. Research: https://pubmed.ncbi.nlm.nih.gov/14533369/ ; https://pmc.ncbi.nlm.nih.gov/articles/PMC3917343/ ; Godot TPS example https://github.com/godotengine/tps-demo/blob/master/player/player.gd . Hand clearance uses a measured skirt envelope and fixed-length arm IK. Original VRM secondary hair/skirt bone identities are retained during asset conversion and constrained against approximate body/hand capsules, with damped return to rest. This is bone-based collision correction, not full cloth or mesh collision; visual tuning is still required.
